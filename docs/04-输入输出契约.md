# Context 工程与需求交付协作 Agent

## 分支与能力模块输入输出契约

> 版本：v0.3
> 阶段：个人 POC  
> 更新日期：2026-08-05
> 上游文档：《用户任务流程设计》v0.3、《Agent 状态机设计》v0.3

---

## 0. 设计目标

输入输出契约用于约束主 Agent、原生 Skill、Harness 脚本、文件型 Context 仓库和本地 Runtime 之间的数据交换，确保：

- 模块边界清晰；
- 每次工具调用可独立评测；
- 下游不依赖自然语言猜测上游结果；
- 未确认内容不会被误当成稳定事实；
- Agent 无法通过自由改写绕过业务规则；
- 状态、版本和来源可以完整追溯；
- 工具失败后可以安全重试和恢复。

POC 阶段所有核心模块优先返回结构化 JSON。面向用户的 Markdown 由外部 Agent 宿主根据 Runtime 返回结果渲染，避免把 Markdown 文本直接作为下游唯一输入。外部 Agent 宿主是可替换的，项目 Runtime 才是业务执行事实源。

## 0.1 外部 Agent Gateway 契约（JSONL 兼容入口）

Gateway 使用 JSONL stdin/stdout 作为 POC 的通用接入协议。每行一个请求，每行一个响应。Gateway 只做协议校验、调用 `AgentOrchestrator.handleMessage()` 和响应包装，不直接调用 Skill、状态机或文件写入脚本。

### 请求

```json
{
  "protocol_version": "0.1",
  "request_id": "req_demo_001",
  "task_id": "demo-task",
  "project_id": "account-settings",
  "session_id": "session_demo",
  "message": "请整理这份会议记录，先不要写 PRD",
  "material_path": "/workspace/materials",
  "client": {
    "id": "generic-external-agent",
    "name": "可替换的外部 Agent",
    "version": "1.0.0"
  }
}
```

字段规则：

- `request_id`：外部宿主生成的单次请求标识，响应必须原样返回；
- `task_id`：继续已有任务时必填，新任务可省略，由 Runtime 创建；
- `session_id`：外部会话标识，只用于关联会话，权威业务状态仍以 Runtime 为准；
- `message`：用户自然语言原文或用户对当前确认的回复；
- `material_path`：可选材料路径，由 Runtime/provider 校验，不代表外部 Agent 获得写权限；
- `client`：宿主元数据，用于审计和验证，不参与业务路由；
- 请求不包含 `target_state`、`approved_actions` 或任意直接写入指令。

`material_path` 只适合外部宿主能够访问同一文件系统的场景。外部 Agent 的主要入口使用下方 MCP Tool，直接传入原始材料，不要求产品经理先创建文件。

### 响应

```json
{
  "protocol_version": "0.1",
  "request_id": "req_demo_001",
  "status": "SUCCESS",
  "agent_response": {
    "message": "已分析材料，等待你确认 Context 更新建议。",
    "state": { "id": "WAITING_CONTEXT_CONFIRM", "name": "等待 Context 更新确认", "type": "waiting" },
  "status": "WAITING_CONFIRMATION",
  "execution_authority": "RUNTIME_ONLY",
  "execution_status": "WAITING_USER_CONFIRMATION",
  "result_is_authoritative": true,
  "external_agent_instruction": "Runtime 尚未完成。只能展示返回的确认项，不得自行整理、写文件或宣称任务完成。",
  "provider": { "id": "workspace", "label": "通用项目工作区 Provider" },
    "artifacts": [],
    "confirmation": { "id": "confirm_demo", "title": "确认稳定 Context 更新建议", "actions": [], "items": [] },
    "next_steps": ["确认全部", "暂不更新稳定 Context"]
  },
  "runtime": {
    "task_id": "demo-task",
    "session_id": "session_demo",
    "current_state": "WAITING_CONTEXT_CONFIRM",
    "provider": "workspace",
    "runtime_version": "0.1.0"
  },
  "error": null
}
```

`status` 枚举：`SUCCESS`、`INVALID_REQUEST`、`RUNTIME_ERROR`。业务上的等待、完成或阻塞由 `agent_response.status` 和 `agent_response.state` 表示。

### 外部宿主确认转发规则

外部 Agent 只能把用户的自然语言确认原文作为下一次 `message` 发送。例如用户说“确认全部”，宿主发送这句话，不能自行把它转换成 `APPROVE_ALL`。Runtime 根据当前状态和待确认记录解析动作，并由 Harness 校验是否允许。

### 替换性与一致性

不同宿主只要遵守该请求/响应契约，就共享同一 `task_id` 下的状态、确认记录、产物引用和事件日志。宿主中断或替换不会创建第二套业务状态。

## 0.2 MCP Tool 契约（主要日常入口）

MCP Server 暴露一个统一工具 `context_delivery`。工具只负责接收用户表达和材料，所有业务判断仍由 `AgentOrchestrator` 完成。

### 请求

```json
{
  "project_id": "product-work",
  "task_id": "search-context-001",
  "session_id": "mcp-session-001",
  "message": "请整理这份会议记录，先不要写 PRD",
  "materials": [
    {
      "name": "会议记录.md",
      "content": "会议确认先整理材料，再由产品经理确认范围……",
      "source_type": "MEETING_NOTE",
      "source_owner": "产品团队",
      "source_time": "2026-08-05T10:00:00+08:00",
      "is_complete": true
    }
  ]
}
```

字段规则：

- `message` 必须是用户原始自然语言；确认轮次仍使用同一个 `task_id`；
- `materials` 是可选数组，`content` 必须保留原文，不接受只传外部 Agent 总结；
- 新建材料整理任务时，`material_path` 和 `materials` 至少提供一个；继续确认、暂停或恢复任务时可以不带材料；
- `name` 必填；`source_type`、`source_owner`、`source_time` 和 `is_complete` 可选，缺失项进入材料登记报告；
- `project_id` 用于项目隔离；省略时使用当前默认项目；
- 请求不得包含 `target_state`、`approved_actions`、`skill`、`resolution` 或直接文件写入参数；
- Adapter 会将内联材料先落盘到 `drafts/`，转换为内部 `content_ref`，然后调用与本地文件相同的 Skill 契约。

### 返回

MCP Tool 返回 `agent_response` 的结构与 JSONL Gateway 中的 `agent_response` 相同，并附带 `task_id`、`session_id` 和 `runtime_version`。外部 Agent 应展示 `message`、中文状态、产物、确认项和 `next_steps`。

Runtime 响应还必须返回 `execution_authority = RUNTIME_ONLY`、`execution_status`、`result_is_authoritative` 和 `external_agent_instruction`。只有 `execution_status = COMPLETED` 且 `artifacts` 非空时，宿主才可以报告完成；`WAITING_USER_CONFIRMATION`、`BLOCKED` 或 `ERROR` 时，宿主必须停止生成或写入替代结果。整理任务的验收以 Runtime 是否在指定 `context-workspace/` 路径生成结构化 artifact 为准，不要求宿主把 artifact 全文复制到聊天消息中。

```json
{
  "message": "已完成材料登记与分析，需要确认 Context 更新建议。",
  "state": { "id": "WAITING_CONTEXT_CONFIRM", "name": "等待 Context 更新确认", "type": "waiting" },
  "status": "WAITING_CONFIRMATION",
  "skill": "material-ingest → context-maintain",
  "artifacts": [],
  "confirmation": {},
  "next_steps": ["确认全部", "暂不更新稳定 Context"],
  "task_id": "search-context-001",
  "session_id": "mcp-session-001",
  "runtime_version": "0.1.0"
}
```

MCP 的 `tools/call` 是唯一需要外部 Agent 关注的协议动作。Adapter 不把 MCP 的工具调用、模型名称或宿主会话写入业务状态；业务状态仍由 Runtime 管理。

### 错误

工具参数错误返回 `isError: true` 和结构化错误码，包括 `INVALID_TOOL_INPUT`、`MATERIAL_MISSING`、`MATERIAL_TOO_LARGE`、`TASK_NOT_FOUND`、`RUNTIME_EXECUTION_ERROR`。输入错误不得改变当前任务状态。

### 外部 Agent 边界

外部 Agent 不得把自己的摘要、内部 function call 参数或模型判断当作 `material-ingest` 结果；必须以工具返回为准。用户确认原文再次传入 `message`，由 Runtime 解析为当前确认状态允许的动作。
外部 Agent 不得在项目根目录创建未被 Runtime 返回的业务文件。所有整理稿、报告和 Context 变更都必须通过 `artifacts` 引用追溯到 `context-workspace/`。

## 1. 全局契约规则

### 1.1 通用请求头 `request_meta`

每次核心能力调用必须携带：

```json
{
  "request_id": "req_20260803_001",
  "idempotency_key": "task_001_material_ingest_v1",
  "user_id": "user_001",
  "project_id": "project_help_center_search",
  "task_id": "task_001",
  "session_id": "session_001",
  "current_state": "CONTEXT_ANALYZING",
  "repository_revision": "a1b2c3d",
  "triggered_by": "USER",
  "requested_at": "2026-08-03T10:00:00+08:00"
}
```

字段规则：

- `request_id`：单次调用唯一标识；
- `idempotency_key`：防止重试时重复写入；
- `current_state`：调用前状态，工具端应校验是否允许调用；
- `repository_revision`：调用开始时的 Git commit，工作区尚无提交时可为 `null`；
- `triggered_by`：`USER`、`AGENT`、`SYSTEM`；
- 任何写操作都必须包含 `idempotency_key`。

### 1.2 通用响应头

```json
{
  "request_id": "req_20260803_001",
  "status": "SUCCESS",
  "summary": "已分析 3 份材料，识别 2 条待确认冲突",
  "artifacts": [],
  "warnings": [],
  "next_action": {
    "recommended_state": "WAITING_CONTEXT_CONFIRM",
    "reason": "存在 2 条可能改变稳定 Context 的建议",
    "requires_user_confirmation": true
  },
  "trace": {
    "skill": "material-ingest",
    "skill_version": "0.1.0",
    "prompt_version": "0.1.0",
    "schema_version": "0.1.0",
    "model": "configured-model-id",
    "git_commit": "a1b2c3d",
    "input_refs": [],
    "output_refs": [],
    "completed_at": "2026-08-03T10:00:10+08:00"
  },
  "error": null
}
```

`status` 枚举：

- `SUCCESS`：调用成功；
- `NEEDS_CONFIRMATION`：结果有效，但需要人工确认；
- `BLOCKED`：缺少必要输入或业务前置条件；
- `PARTIAL_SUCCESS`：部分材料或子任务成功；
- `ERROR`：调用失败。

### 1.3 决策理由规则

所有路由和建议必须返回简洁、可核验的 `reason`，说明引用了什么事实和规则，但不要求输出模型隐藏的完整思维过程。

合格示例：

> 用户明确要求“只整理、不写 PRD”，且当前没有变更请求，因此路由至 Context 整理模式。

不合格示例：

> 经过详细思考，我认为这样更好。

### 1.4 来源引用规则

每条事实、决策、冲突和审核问题都必须关联来源引用：

```json
{
  "source_id": "src_meeting_20260801",
  "source_type": "MEETING_NOTE",
  "location": "第 3 段",
  "source_time": "2026-08-01T15:00:00+08:00",
  "quote": "本期暂不扩展未确认的自动化能力"
}
```

没有来源的信息只能标记为推测、建议或待确认，不能标记为已确认事实。

### 1.5 版本规则

所有可变产物至少包含：

- `artifact_id`；
- `version`；
- `previous_version`；
- `created_by`；
- `created_at`；
- `source_refs`；
- `change_summary`。

补充规则：

- Prompt、Skill、Schema 和 Markdown 产物使用 frontmatter 中的语义版本；
- 同一逻辑产物保持稳定路径，依赖 Git 历史查看旧版本，不创建 `v1`、`v2`、`final` 等重复文件；
- 关键人工确认、稳定 Context 写入、PRD 阶段完成和评测发布可创建 Git checkpoint；
- Runtime 状态变化只记录在 JSON/JSONL，不要求每次状态转移都创建 Git commit；
- 评测结果必须绑定 Git commit、Prompt 版本、Skill 版本、Schema 版本、模型和评测集版本。

### 1.6 文件引用规则

跨模块引用统一使用仓库相对引用，例如：

```json
{
  "ref": "repo://context-workspace/context/product-work/business-rules/boundary.md",
  "version": "1.2.0",
  "git_commit": "a1b2c3d"
}
```

- `repo://` 后的路径必须位于项目仓库内；
- 引用必须同时携带逻辑版本或 Git commit，不能只传脱离版本信息的文本片段；
- Runtime 文件使用 `runtime://` 引用，但不得写入公开评测结果中的敏感内容；
- 写入前由 `validate-context-write.ts` 校验目标路径、基线版本、确认记录和允许动作。

## 2. 主 Agent 意图路由契约

### 2.1 输入

```json
{
  "request_meta": {},
  "user_message": "先帮我整理这些资料，不要写 PRD",

    "has_context": true,
    "has_workspace": true,

  }
```

### 2.2 输出

```json
{
  "detected_intent": "ORGANIZE_CONTEXT",
  "confidence": 0.98,
  "route_target": "CONTEXT_ANALYZING",
```

`detected_intent` 枚举：

## 3. `material-ingest` 契约

### 3.1 职责

接收和登记原始材料，提取信息单元并给出初步成熟度分类，不直接修改稳定 Context。

### 3.2 输入

```json
{
  "request_meta": {},
    "task_goal": "整理项目材料，不生成 PRD",
  "analysis_scope": {
    "topic": "项目材料整理",
    "time_range": null,
    "included_source_ids": ["src_001", "src_002"]
  },
  "materials": [
    {
      "source_id": "src_001",
      "name": "会议记录.md",
      "source_type": "MEETING_NOTE",
      "source_owner": "产品团队",
      "source_time": "2026-08-01T15:00:00+08:00",
      "content_ref": "repo://context-workspace/drafts/search-discussion.md",
      "is_complete": true
    }
  ],
  "existing_context_refs": ["context://search/current_state"],
  "existing_workspace_refs": ["workspace://search/current_task"]
}
```

### 3.3 输出

```json
{
  "material_records": [
    {
      "source_id": "src_001",
      "topic": "项目材料整理",
      "processing_status": "PROCESSED",
      "missing_metadata": []
    }
  ],
  "information_items": [
    {
      "item_id": "info_001",
      "content": "部分用户使用口语词搜索时无法命中已有文章",
      "information_type": "OBSERVATION",
      "maturity": "UNCONFIRMED",
      "source_refs": ["src_001"],
      "target_layer": "WORKSPACE",
      "confidence": 0.92,
      "requires_confirmation": false
    }
  ],
  "processing_summary": {
    "material_count": 2,
    "processed_count": 2,
    "failed_count": 0,
    "information_item_count": 8
  },
  "failed_materials": []
}
```

`information_type` 枚举：

- `USER_FEEDBACK`；
- `OBSERVATION`；
- `FACT`；
- `DATA`；
- `OPINION`；
- `PROPOSAL`；
- `CONFIRMED_DECISION`；
- `OPEN_QUESTION`；
- `DEPRECATED_CONTENT`。

`maturity` 枚举：

- `RAW`；
- `UNCONFIRMED`；
- `CONFIRMED`；
- `SUPERSEDED`；
- `ARCHIVED`。

边界：

- 不能根据语言语气自行认定“已确认”；
- “会议里有人提出”默认是 `PROPOSAL` 或 `OPINION`；
- 缺少来源或时间的内容只能进入 `DRAFTS`；
- 输出必须保留来源关联。

## 4. `context-maintain` 契约

### 4.1 职责

读取材料分析结果和现有 Context，检查冲突、重复、过期、索引和生命周期，先生成更新建议，再根据人工批准结果执行维护。

该模块包含两个动作：

- `ANALYZE`：只分析并生成建议；
- `APPLY`：只执行已获批建议。

### 4.2 `ANALYZE` 输入

```json
{
  "request_meta": {},
  "action": "ANALYZE",
  "information_items": [],
  "context_snapshot": {
    "version": "context_v3",
    "index_ref": "context://index/v3",
    "content_refs": []
  },
  "workspace_snapshot": {
    "version": "workspace_v5",
    "content_refs": []
  },
  "checks": [
    "DUPLICATE",
    "CONFLICT",
    "STALE_CONTENT",
    "TERMINOLOGY",
    "INDEX_CONSISTENCY",
    "BROKEN_REFERENCE"
  ]
}
```

### 4.3 `ANALYZE` 输出

```json
{
  "update_proposals": [
    {
      "proposal_id": "proposal_001",
      "action": "PROMOTE_TO_CONTEXT",
      "target_ref": "context://search/boundaries",
      "item_id": "info_006",
      "current_value": null,
      "proposed_value": "本期不扩展到未确认的自动化能力",
      "source_refs": ["src_001"],
      "relationship": "NEW",
      "risk_level": "HIGH",
      "requires_confirmation": true,
      "impact_if_applied": "后续任务将默认遵守已确认的范围边界",
      "impact_if_ignored": "后续任务可能再次把未确认能力纳入范围"
    }
  ],
  "conflicts": [],
  "stale_items": [],
  "index_issues": [],
  "auto_actions": [],
  "remaining_questions": []
}
```

更新动作枚举：

- `WRITE_DRAFT`；
- `WRITE_WORKSPACE`；
- `PROMOTE_TO_CONTEXT`；
- `UPDATE_CONTEXT`；
- `MARK_SUPERSEDED`；
- `ARCHIVE`；
- `UPDATE_INDEX`；
- `FIX_REFERENCE`；
- `NO_ACTION`。

### 4.4 `APPLY` 输入

```json
{
  "request_meta": {},
  "action": "APPLY",
  "base_context_version": "context_v3",
  "approved_actions": [
    {
      "proposal_id": "proposal_001",
      "approval_status": "APPROVED",
      "approved_by": "user_001",
      "approved_at": "2026-08-03T10:10:00+08:00",
      "user_modification": null
    }
  ]
}
```

### 4.5 `APPLY` 输出

```json
{
  "executed_actions": ["proposal_001"],
  "skipped_actions": [],
  "failed_actions": [],
  "new_context_version": "context_v4",
  "new_index_version": "context_index_v4",
  "change_log_ref": "repo://context-workspace/workspace/context-change-log.md",
  "health_check": {
    "status": "PASS",
    "remaining_issues": []
  }
}
```

边界：

- `APPLY` 不得执行输入中不存在的动作；
- 不得执行 `PENDING` 或 `REJECTED` 建议；
- `base_context_version` 与当前版本不一致时返回版本冲突；
- 高风险变更执行前必须创建快照；

### 8.1 职责

### 8.2 输入

```json
  "request_meta": {},

    "context_version": "context_v4",
    "decision_ledger_version": "decision_v3",
    "prd_version": "prd_v0.1-core"
  },
  "artifact_refs": [],
  "confirmed_decision_refs": []
}
```

```json
{
  "change_classification": {
    "change_type": "SCOPE_CHANGE",
    "is_material_change": true,
    "confidence": 0.99
  },
  "change_summary": {

      "artifact_ref": "repo://context-workspace/workspace/prd/product-work.md",
      "locations": ["产品目标", "本期范围", "核心流程"],

      "reason": "核心方案和用户流程发生变化"

  "risks": [],

```

`change_type` 枚举：

- `SOURCE_CHANGE`；
- `FACT_CHANGE`；
- `GOAL_CHANGE`；
- `SCOPE_CHANGE`；
- `DECISION_CHANGE`；
- `CORE_FLOW_CHANGE`；
- `DETAIL_RULE_CHANGE`；
- `WORDING_ONLY`；

POC 实现将输出拆成两个可独立校验的模式：

- `ANALYZE`：保存 `snapshot_ref`、变化分类、影响项、保留项和推荐返回节点；

边界：

- 输出新计划前必须引用当前快照；
- 不得直接更新 Context、决策账本或 PRD；
- 必须明确不受影响内容，避免无差别重写；
- `UNKNOWN` 时不得自行选择返回节点；
- 重规划计划必须等待 CP-R01 确认。

## 9. 人工确认契约

所有人工确认使用统一结构：

```json
{
  "confirmation_id": "confirm_001",
  "confirmation_type": "INTENT_CLARIFICATION",
  "task_id": "task_001",
  "current_state": "WAITING_INTENT_CLARIFICATION",
  "return_state": "INTENT_ROUTING",
  "title": "确认本次任务目标",
  "items": [],
  "allowed_actions": [
    "ORGANIZE_CONTEXT_ONLY",
    "PREPARE_PRD",
    "MODIFY_EXISTING_TASK",
    "START_NEW_TASK",
    "PAUSE",
    "CANCEL"
  ],
  "status": "PENDING",
  "resolved_by": null,
  "resolved_at": null,
  "resolution": null
}
```

`confirmation_type` 枚举：

- `RESUME_CHOICE`；
- `INTENT_CLARIFICATION`；
- `CONTEXT_UPDATE`；
- `DECISION_AND_WRITABLE_STATUS`；
- `SCOPE_AND_CORE_FLOW`；
- `REVIEW_DISPOSITION`；
- `REPLAN_APPROVAL`。

确认类型与等待状态的固定对应关系：

| `current_state` | `confirmation_type` | 说明 |
|---|---|---|
| `WAITING_RESUME_CHOICE` | `RESUME_CHOICE` | 选择继续、调整、放弃或新建 |
| `WAITING_INTENT_CLARIFICATION` | `INTENT_CLARIFICATION` | 选择只整理、准备 PRD、修改已有任务或新建任务 |
| `WAITING_MATERIAL_REPROCESS_CONFIRM` | `MATERIAL_REPROCESS` | 检测到相同材料已整理过，确认是否重新整理并覆盖整理稿 |
| `WAITING_CONTEXT_CONFIRM` | `CONTEXT_UPDATE` | 确认稳定 Context 的提升、覆盖、失效或归档 |
| `WAITING_DECISION_CONFIRM` | `DECISION_AND_WRITABLE_STATUS` | 确认目标、范围、关键决策和可写状态 |
| `WAITING_SCOPE_CONFIRM` | `SCOPE_AND_CORE_FLOW` | 确认 PRD 主体范围和核心流程 |
| `WAITING_REVIEW_DECISION` | `REVIEW_DISPOSITION` | 处理审核建议并决定是否交付 |
| `WAITING_REPLAN_CONFIRM` | `REPLAN_APPROVAL` | 确认影响分析后的新计划 |

`WAITING_CONTEXT_CONFIRM` 如果由 `WAITING_REVIEW_DECISION` 触发，必须在确认记录中写明 `source_state = "WAITING_REVIEW_DECISION"` 和 `return_state = "DELIVERED"`。这表示用户已经选择交付，但交付前存在待处理的稳定 Context 回写建议；它不是审核状态自动跳转到 Context 维护。

Context 确认必须按 proposal 逐项解析。用户可以明确指定 `proposal_id` 或编号批准某些建议，并在同一条消息中说明其他建议“暂不更新”或“拒绝”；负面措辞不能覆盖同一消息中的明确批准项。没有识别出具体 proposal 时 Runtime 必须停留在 `WAITING_CONTEXT_CONFIRM`，不得按“确认”前缀推断为全量批准。

已写入稳定 Context 的撤销也必须重新进入 CP-C01。撤销动作使用 `ARCHIVE`，只将文件标记为 `status: archived` 并从 Context 索引隐藏，保留原文件、来源和版本记录，不允许通过外部 Agent 直接删除业务文件。

`return_state` 不允许由模型自由填写。Harness 只接受状态机配置中的返回状态白名单：

- `source_state = CONTEXT_ANALYZING`：`CONTEXT_TASK_COMPLETED` 或 `PRD_THINKING`；
- `source_state = WAITING_REVIEW_DECISION`：`DELIVERED`；
- 其他来源：必须在状态机配置中显式登记，默认拒绝。

规则：

- 等待状态必须关联一个未完成确认记录；
- 用户回复必须解析为允许动作之一；
- 无法解析时保持 `PENDING`；
- 用户沉默不能自动变成批准；
- 确认记录一旦完成不可原地覆盖，只能创建修订记录。

## 10. 错误契约

```json
{
  "status": "ERROR",
  "error": {
    "code": "CONTEXT_VERSION_CONFLICT",
    "message": "Context 已被其他操作更新，请重新读取后再执行",
    "retryable": true,
    "failed_step": "context-maintain/APPLY",
    "last_valid_state": "WAITING_CONTEXT_CONFIRM",
    "recovery_action": "RELOAD_AND_REANALYZE",
    "details_ref": "runtime://errors/error_001.json"
  }
}
```

POC 核心错误码：

| 错误码 | 含义 | 推荐处理 |
|---|---|---|
| `INTENT_AMBIGUOUS` | 用户目标不明确 | 进入意图澄清 |
| `MATERIAL_MISSING` | 缺少任务材料 | 阻塞并要求补充 |
| `MATERIAL_TOO_LARGE` | 内联材料超过 POC 限制 | 分批提交或使用 `material_path` |
| `INVALID_TOOL_INPUT` | MCP Tool 参数不符合契约 | 修正请求，不改变任务状态 |
| `TASK_NOT_FOUND` | 指定任务不存在或不属于当前项目 | 重新创建任务或确认 task_id |
| `SOURCE_UNVERIFIED` | 来源无法核实 | 保留在 drafts |
| `CONTEXT_CONFLICT` | 新旧 Context 冲突 | 等待人工确认 |
| `CONTEXT_CONFIRM_REQUIRED` | 稳定写入未获批准 | 拒绝写入 |
| `CONTEXT_VERSION_CONFLICT` | 写入基线版本已变化 | 重新读取和分析 |
| `PRD_NOT_WRITABLE` | 未达到可写状态 | 返回写前对齐 |
| `SCOPE_NOT_CONFIRMED` | 主体范围未确认 | 禁止补充细节 |
| `ILLEGAL_STATE_TRANSITION` | 状态跳转不合法 | 保留原状态并记录 |
| `TOOL_EXECUTION_FAILED` | 工具执行失败 | 重试，达到上限后阻塞 |
| `REPLAN_LIMIT_REACHED` | 重规划次数达到上限 | 暂停并等待人工处理 |
| `RESTORE_DATA_INCOMPLETE` | 恢复所需状态不完整 | 展示可恢复点并确认 |

## 11. 分支级输入输出摘要

| 分支/能力 | 核心输入 | 核心输出 | 下一状态由什么决定 |
|---|---|---|---|
| 意图路由 | 用户消息、附件、活动任务、项目摘要 | 意图、置信度、路由目标、理由 | 意图和任务恢复状态 |
| Context 整理 | 原始材料、已有 Context、分析范围 | 信息分类、冲突、更新建议 | 是否涉及稳定 Context 变化 |
| Context 维护 | 获批动作、Context 基线版本 | 新版本、索引、变更日志、健康检查 | 用户目标是结束还是继续 PRD |
| PRD 写前对齐 | 问题、Context、workspace、历史 PRD | 背景卡、决策账本、可写状态 | 是否存在阻塞和人工确认结果 |
| PRD 写作 | 已确认决策、范围、阶段、现有版本 | 主体或细节版本、覆盖情况、待确认项 | 当前写作阶段和人工确认结果 |
| PRD 审核 | 完整 PRD、Context、决策账本 | 分级问题、依据、建议和审核结论 | 用户处理决定 |
| 变更影响 | 变更请求、任务快照、产物版本 | 影响范围、返回节点、新计划 | 变更类型和人工确认结果 |

## 12. 契约评测要求

每个模块至少验证：

- 必填字段缺失时返回明确错误；
- 枚举字段只能返回合法值；
- 每条事实和决策保留来源；
- 状态与工具调用权限一致；
- 写操作支持幂等；
- 重试不会产生重复版本；
- 未确认信息不会进入稳定 Context；
- `prd-thinking` 不输出 PRD 正文；
- `prd-review` 不直接修改 PRD；
- `change-impact` 不直接覆盖当前版本；
- 下游能够仅依赖结构化输出继续执行；
- Markdown 展示内容与结构化数据一致。
- 评测记录能够由 Git commit、Skill/Prompt/Schema 版本和模型配置复现。
- 外部 Agent 的 `tools/call` 记录能够证明 Runtime 实际执行，并且材料原文可追溯到 `drafts/`。
