# Context 工程与需求交付协作 Agent

## 产品定义与 POC 最小验证范围

> 版本：v1.2
> 阶段：个人 POC  
> 更新日期：2026-08-05
> 默认形态：通用项目工作区；业务材料：由用户在当前任务中提供

---

## 0. 执行摘要

Context 工程与需求交付协作 Agent 是面向单人产品经理的 AI 工作台。系统将会议记录、用户反馈、历史 PRD、产品现状和业务约束等分散材料，转化为可持续维护、可被 AI 正确使用的 Context；在此基础上，根据用户目标、材料成熟度、历史决策和当前任务状态，动态编排 Context 整理维护与需求分析、PRD 交付能力。

系统不替产品经理判断需求是否值得做，也不替人决定业务优先级、产品范围和关键取舍。涉及事实确认、范围变化和业务边界调整时，Agent 必须暂停并等待人工决策。

本阶段以个人 POC 形式，重点验证以下核心假设：

1. Agent 能否根据用户意图和材料状态，正确选择 Context 整理或 PRD 交付任务。
2. Agent 能否区分原始反馈、事实、方案提议、已确认决策和待确认问题。
3. Agent 能否在材料不足或存在冲突时停止生成，并提出有依据的定向问题。
4. Agent 能否在用户修改需求后完成影响分析、重规划和局部更新。
5. Context、状态和未完成任务能否跨会话保存并恢复。
6. Harness 能否通过状态、工具、权限、人工确认和日志机制约束 Agent 行为。

## 1. 产品定义

### 1.0 产品架构定位

本项目采用“外部 Agent 宿主 + 项目 Runtime”的产品形态：

- 外部 Agent 是可替换的自然语言交互宿主，负责理解表达、追问、收集确认和展示结果；
- MCP Adapter 是面向 Claude、Codex、Cursor 等外部 Agent 的主要工具适配层；JSONL Gateway 是兼容客户端和回归测试适配层；两者都只负责协议转换、调用 Runtime 和包装响应；
- 项目 Runtime 是唯一的业务编排与执行中心，负责意图路由、状态机、Skill 编排、人工确认、Harness 校验、Context/PRD 受控写入、版本、日志和评测；
- 外部 Agent 不直接修改业务产物、不保存权威任务状态，也不自行决定状态转移。

因此，本项目不是某个厂商 Agent 的 Prompt 集合，也不是六个 Skill 的简单拼接，而是可以被不同自然语言宿主调用的领域 Agent Runtime。

### 1.1 产品名称

**Context 工程与需求交付协作 Agent**

### 1.2 一句话定位

面向需要长期维护产品上下文并交付需求文档的产品经理，通过 Context 工程积累可信业务知识，由主 Agent 动态编排资料整理、需求分析和 PRD 交付，并在关键业务判断节点等待人工确认。

### 1.3 产品形态

本产品不是单一 PRD 生成器，而是由以下部分组成的 AI 工作台：

- 面向用户的业务 Agent；
- 由 `drafts/`、`workspace/`、`context/` 构成的文件型 Context 工作空间；
- 通过 `AGENTS.md` 注册和路由的 6 个原生 Skill；
- 由状态机、权限、人工确认、日志和确定性脚本组成的本地 Agent Harness；
- 保存当前任务快照、待确认项和追加事件日志的本地 Runtime；
- 用于版本追溯、评测绑定和作品展示的 Git/GitHub 仓库。

外部交互入口以 MCP Tool 为主要日常入口，同时保留 JSONL Gateway 和 CLI Adapter。三种入口都调用同一个 Runtime；更换宿主不改变业务状态、确认门禁和产物路径。MCP、Gateway 和 CLI 不是三个 Agent，也不复制业务编排逻辑。

### 1.3.1 外部 Agent 自然语言使用闭环

产品经理只需要在外部 Agent 中输入自然语言，外部 Agent 必须调用本项目提供的 `context_delivery` 工具，并将用户原文、项目标识、任务标识和原始材料交给 Runtime：

```text
产品经理输入自然语言和材料
    ↓
外部 Agent 调用 context_delivery
    ↓
MCP Adapter 校验请求并调用 AgentOrchestrator
    ↓
Runtime 执行 material-ingest / context-maintain / PRD / Change 分支
    ↓
Runtime 返回状态、Skill、产物和确认点
    ↓
外部 Agent 展示结果；确认回复再次调用同一 task_id
```

外部 Agent 没有调用工具时，不能把自己的总结当成本项目的执行结果；只有 Runtime 返回的状态、产物和确认记录才属于本项目的业务结果。

### 1.4 产品阶段

当前阶段为 **个人 POC**。

POC 验证的是产品方案与 Agent 架构是否成立，不验证真实企业上线效果、规模化稳定性和业务 ROI。

## 2. 目标用户

### 2.1 核心用户

需要处理多源需求材料、长期维护产品上下文，并使用 AI 辅助完成需求分析和 PRD 交付的单人产品经理。

POC 阶段聚焦以下特征：

- 负责相对复杂的 B 端或跨角色需求；
- 日常需要处理会议记录、用户反馈、历史 PRD 和业务规则；
- 已经使用通用 AI 工具辅助总结、分析或写作；
- 需求交付过程中存在多轮确认、范围调整和历史信息复用。

### 2.2 非目标用户

- 只需要生成一次简单文案的用户；
- 只需要固定 PRD 模板填充的用户；
- 希望 AI 自动决定需求价值和优先级的用户；
- 需要多人权限、组织知识治理和完整协作平台的团队。

## 3. 核心问题

### 3.1 Context 缺失

产品背景、用户反馈、历史决策、业务术语和技术约束分散在不同材料中。每次使用 AI 都需要重新解释，AI 也容易因缺少关键背景而输出通用、错误或过期的内容。

### 3.2 信息状态混乱

原始反馈、数据口径、讨论方案、已确认结论和废弃方案经常混在一起。AI 无法判断哪些内容可以相信，容易把“有人提过”写成“团队已经决定”。

### 3.3 需求交付容易走样

从业务材料到 PRD 的过程中，范围、异常、上下游、验收条件和待确认项容易遗漏；一次性生成完整 PRD 后再修改，返工成本较高。

### 3.4 需求变化缺少影响管理

当目标、范围或业务规则发生变化时，相关 Context、PRD 章节、验收用例和上下游依赖难以同步更新，容易出现版本不一致。

### 3.5 AI 工作过程缺少持续状态

普通对话工具不知道当前任务做到哪里、哪些决策已经确认、下一步应该做什么，也缺少跨会话恢复、合法状态约束和过程追溯能力。

## 4. 产品目标与非目标

### 4.1 产品目标

1. 将分散材料转化为分层、可信、可持续维护的 Context。
2. 让 Agent 根据用户目标和材料状态选择正确的下一步，而不是固定执行完整流程。
3. 在写 PRD 前显性化背景、范围、关键决策和信息缺口。
4. 将已确认判断稳定展开为可评审、可交付的 PRD。
5. 在需求变化时识别影响范围并重新规划，避免整份文档无差别重写。
6. 将任务中产生的新事实、决策和错误经验沉淀回 Context、Skill 或 Harness，形成持续改进闭环。

### 4.2 产品非目标

本产品不负责：

- 判断一个需求是否值得做；
- 决定业务优先级和资源投入；
- 替代用户访谈、数据分析和市场验证；
- 将用户原话直接定义为需求；
- 自动推翻人工确认的业务决策；
- 未经确认修改稳定业务事实和边界；
- 自动写入第三方生产系统；
- 证明真实业务提效或 ROI。

## 5. 核心价值

### 5.1 对用户的价值

- 减少每次向 AI 重复解释产品背景的成本；
- 降低信息错位、过期 Context 和范围遗漏带来的返工；
- 将隐含决策提前显性化，使问题在写 PRD 前暴露；
- 保留需求形成、修改和确认过程，便于后续追溯；
- 允许用户只维护 Context，不强制进入 PRD 生成。

### 5.2 产品核心价值主张

> 不替产品经理做业务判断，而是管理 AI 判断所需的 Context，暴露信息缺口，并将已经确认的判断稳定转化为可交付成果。

### 5.3 数据闭环

```text
业务材料进入
    ↓
Context 积累
    ↓
任务输出质量提升
    ↓
产生新事实、决策和 Bad Case
    ↓
判断应更新 Context、Skill 还是 Harness
    ↓
下一次同类任务减少重复错误
```

## 6. 产品结构

本产品由两类用户任务模式和一个全局 Agent 能力构成。

### 6.1 用户任务模式 A：Context 整理与维护

用户可以只要求整理资料，不进入 PRD 交付。

核心能力：

- 接收会议记录、用户反馈、历史 PRD、业务说明和约束材料；
- 识别材料类型、主题、来源、时间和可信状态；
- 区分事实、反馈、观点、方案提议、已确认决策和待确认项；
- 检查重复、冲突、术语不一致和过期内容；
- 将信息建议放入 `drafts/`、`workspace/` 或 `context/`；
- 在人工确认后更新稳定 Context；
- 更新索引、引用、版本和替代关系；
- 对 Context 工作空间执行健康检查。

主要输出：

- 材料分类报告；
- 由 Runtime 生成的结构化材料整理稿（会议记录、用户反馈等）；
- 信息成熟度清单；
- 冲突与待确认清单；
- Context 更新建议；
- 更新后的 Context 索引；
- Context 健康检查报告。

### 6.2 用户任务模式 B：需求分析与 PRD 交付

该模式建立在已有业务材料和人工判断基础上，不从一句模糊想法直接生成完整 PRD。

核心流程：

```text
读取相关 Context 和当前材料
    ↓
生成背景理解卡
    ↓
生成关键决策账本
    ↓
判断是否达到可写状态
    ↓
人工确认目标、范围和关键决策
    ↓
生成 PRD 主体
    ↓
人工确认范围和核心流程
    ↓
补充异常、验收、依赖和风险
    ↓
独立审核
    ↓
人工决定修改或交付
```

主要输出：

- 背景理解卡；
- 决策账本；
- 可写状态判断；
- PRD 主体；
- PRD 细节；
- 独立审核报告；
- 待确认问题清单；
- 最终 PRD。

### 6.3 全局 Agent 能力：修改、影响分析与重规划

修改与重规划不是独立业务终点，而是可以从任意任务阶段触发的全局控制能力。

触发条件：

- 用户改变目标、范围或关键决策；
- 新材料与已有 Context 冲突；
- 审核发现 P0/P1 问题；
- 已有执行计划不再适用；
- 用户跨会话恢复后选择调整原任务。

核心能力：

- 识别发生变化的事实或决策；
- 分析受影响的 Context、PRD 章节、验收项和上下游依赖；
- 区分需要修改与仍然有效的内容；
- 生成新的执行计划；
- 等待人工确认后返回对应任务节点；
- 保存修改原因、版本差异和新的决策状态。

主要输出：

- 变更内容摘要；
- 影响范围报告；
- 新执行计划；
- 待确认变更清单；
- 修改后的 Context 或 PRD；
- 版本和决策变更记录。

## 7. 人机分工

### 7.1 人负责

- 问题是否成立；
- 需求是否值得做；
- 业务目标和优先级；
- 本期范围与非范围；
- 关键业务规则和产品取舍；
- 哪些信息可以成为稳定 Context；
- 是否采纳审核和重规划建议；
- 最终交付物是否通过。

### 7.2 AI 负责

- 检索和整理材料；
- 分类信息状态；
- 识别重复、冲突和信息缺口；
- 将隐含决策显性化并提供建议；
- 判断流程是否达到下一阶段的准入条件；
- 展开 PRD 结构、规则、异常、验收和依赖；
- 独立审核和一致性检查；
- 分析变更影响并生成重规划建议；
- 保存状态、日志和过程产物。

### 7.3 人工确认原则

> 可逆的整理动作可以自动执行；会改变 AI“相信什么”的动作必须由人确认。

允许自动执行：

- 原始材料写入 `drafts/`；
- 当前任务材料写入 `workspace/`；
- 建立或更新索引草案；
- 标记重复、冲突、待确认和可能过期内容；
- 生成 Context 更新建议和修改建议。

必须人工确认：

- 将信息提升为 `context/` 中的稳定事实；
- 覆盖现有事实或业务规则；
- 修改已确认的业务边界；
- 将旧决策标记为失效；
- 删除或归档仍可能影响当前判断的内容；
- 确认 PRD 范围、核心流程和最终版本。

## 8. Context 生命周期

### 8.1 三层工作空间

```text
drafts/
  原始材料、零散想法、未经确认的信息

workspace/
  当前项目、进行中的需求、讨论记录、待确认事项

context/
  已确认、可复用、可作为当前事实使用的业务知识和边界
```

### 8.2 生命周期

```text
原始材料
→ drafts
→ 当前任务使用
→ workspace
→ 人工确认
→ context
→ 业务发生变化
→ 更新、替代或归档
```

### 8.3 Context 质量要求

- 每条稳定信息应有明确来源；
- 待确认信息不能作为确定事实使用；
- 同一业务事实应有唯一可信版本；
- 过期内容不能与当前事实并列；
- 被替代内容应保留替代关系或归档记录；
- 索引必须与实际材料保持一致；
- 术语、编号和跨文档引用应保持一致。

## 9. Agent 与 Harness

### 9.1 主 Agent 职责

- 理解用户当前目标；
- 读取项目、材料和任务状态；
- 判断当前可执行的动作；
- 选择 Context 整理或 PRD 交付模式；
- 选择并调用对应 Skill；
- 在材料不足或需要业务判断时暂停；
- 触发影响分析和重规划；
- 保存任务状态并支持跨会话恢复；
- 向用户说明当前状态、下一步和需要确认的内容。

### 9.2 轻量 Harness 组成

- `AGENTS.md` 中的全局规则、Skill 注册和路由约束；
- Context 加载顺序和可信度规则；
- Skill 注册、触发条件和输入输出协议；
- 状态机和合法状态转移校验；
- 人工确认和写入权限；
- `runtime/task-state.json`、`runtime/pending-confirmations.json` 和 `runtime/task-events.jsonl` 的运行时持久化；
- `transition-state.ts`、`validate-context-write.ts` 等确定性控制脚本；
- 重试、暂停、恢复和失败兜底；
- 路由理由、工具调用和结果日志；
- 评测、Bad Case 归因和回归机制。

### 9.3 Agent 与 Harness 边界

- Agent 决定“当前应该做什么”；
- Harness 规定“哪些动作允许执行、需要什么前置条件、结果如何记录和校验”。
- Skill 负责“某类专业任务如何完成”，不拥有全局状态和跨 Skill 编排权。

### 9.4 文件、Runtime 与 Git 的职责边界

- `context-workspace/` 是材料、业务 Context、决策和交付产物的运行时事实源；“整理完成”必须以 Runtime 返回 `COMPLETED`、终态 `CONTEXT_TASK_COMPLETED` 和至少一个 `context-workspace/` artifact 为准。外部 Agent 不得自行创建项目外部整理文件或在 Runtime 阻塞时补写结果。
- `runtime/` 是当前任务状态、待确认项和执行事件的运行时事实源；
- Git 保存有意义的内容版本和代码版本，不替代正在运行的任务状态；
- GitHub 用于远程备份、协作记录和脱敏后的作品展示；
- `.env`、密钥、本地运行时状态、待确认记录和敏感原始材料不得提交到公开仓库。

## 10. 核心 Skill

POC 阶段收敛为 6 个核心能力模块：

| Skill | 核心职责 | 主要输出 |
|---|---|---|
| `material-ingest` | 接收、分类和标注原始材料 | 材料清单、信息分类、成熟度标签 |
| `context-maintain` | 查重、冲突检查、生命周期、索引和健康检查 | 冲突报告、更新建议、索引、健康报告 |
| `prd-thinking` | 写前背景与决策对齐 | 背景理解卡、决策账本、可写状态 |
| `prd-write` | 两阶段生成 PRD | PRD 主体、异常、验收和依赖 |
| `prd-review` | 独立审核 PRD | 分级审核报告、修改建议 |
| `change-impact` | 分析需求变化并生成重规划建议 | 影响范围、新计划、差异记录 |

其中：

- 每个 Skill 以独立目录保存说明、Prompt、Schema、示例和测试；
- 主 Agent 根据用户目标、当前状态和前置条件选择 Skill；
- Skill 返回结构化建议，但不能绕过 Harness 直接修改全局状态；
- Harness 保证调用、状态、权限、文件写入和日志规则生效。

## 11. POC 范围

### 11.1 本期做

- 单用户；
- 单项目运行时，可通过 `project_id` 切换不同业务项目；
- 一套与业务无关的隔离回归夹具，不作为面试或日常工作案例；

## 13. 高层状态设计

```text
    初始化
        ↓
    意图识别与任务路由
        ├── 等待恢复选择（存在未完成任务）
        └── 等待任务意图澄清（目标不明确）
    ├── Context 分析中
    │       ↓
    │   等待 Context 更新确认
    │       ↓
    │   Context 维护中
    │       ↓
    │   Context 整理任务已完成
    │
    └── PRD 写前对齐中
            ↓
        等待关键决策确认
            ↓
        PRD 主体生成中
            ↓
        等待范围与核心流程确认
            ↓
        PRD 细节补充中
            ↓
        PRD 独立审核中
            ↓
        等待审核处理决定
            ├── 需求交付已完成（无稳定 Context 回写）
            └── 等待 Context 更新确认
                    ↓
                Context 维护中
                    ↓
                需求交付已完成

任意执行或等待状态
    ├── 任务已暂停
    ├── 执行遇到阻塞
    └── 任务已取消

任意可修改状态
    ↓
变更影响分析中
    ↓
重新规划中
    ↓
等待重规划方案确认
    ↓
返回对应任务节点
```

产品文档和用户界面统一使用中文状态名称。技术实现时为每个状态配置稳定的英文枚举，例如 `初始化 = INITIALIZING`、`等待范围与核心流程确认 = WAITING_SCOPE_CONFIRM`，用于本地 JSON 状态存储、脚本参数、状态校验和评测日志，避免展示文案调整影响程序逻辑。

POC 实施阶段需要进一步定义每个状态的：

- 进入条件；
- 允许调用的工具；
- 必须保存的数据；
- 合法下一状态；
- 人工确认要求；
- 超时、失败和恢复策略。

其中，`TASK_CANCELLED` 在本 POC 中仅表示关闭当前任务并保留历史，不包含删除文件、回滚版本或撤销已执行写入。

## 14. 核心假设

| 编号 | 核心假设 | POC 验证方式 |
|---|---|---|
| H-001 | 多源产品材料可以被可靠分类为不同成熟度和可信状态 | 构造带标准答案的材料分类用例 |

## 15. POC 评测范围

### 15.1 评测维度

#### Agent 路由与状态

- 用户意图识别准确率；
- 任务模式路由准确率；
- Skill 选择准确率；
- 状态转移合法率；
- 暂停和人工确认触发准确率；
- 跨会话状态恢复准确率。
- 暂停、阻塞和取消状态的进入条件及恢复限制正确率。

#### Context 质量

- 信息成熟度分类准确率；
- 事实、观点、提议、决策和待确认项区分准确率；
- 冲突识别率；
- 过期内容识别率；
- 索引与实际内容一致率；
- 未经确认提升为稳定 Context 的次数；
- Context 补充前后的同类错误复现情况。

#### PRD 交付

- 未达到可写状态时的错误放行次数；
- 未确认信息被写成事实的次数；
- 范围和非范围覆盖情况；
- 异常、空态、验收和上下游依赖覆盖情况；
- 跨章节术语、编号和引用一致性；
- 独立审核问题检出情况。

#### 修改与重规划

- 变更识别准确率；
- 受影响内容覆盖率；
- 无关内容保留率；
- 重规划路径正确率；
- 版本和决策记录完整性。

### 15.2 POC 建议验收标准

- 设计并执行 10 至 12 个测试用例；
- 两类用户任务模式路由准确率不低于 90%；
- 状态转移合法率 100%；
- 未经人工确认写入稳定 Context 的次数为 0；
- 未达到可写状态却生成完整 PRD 的次数为 0；
- 预设材料冲突识别率不低于 80%；
- 信息状态分类准确率不低于 85%；
- 变更影响项覆盖率不低于 80%；
- 跨会话任务状态恢复成功率 100%；
- 取消任务后历史和已生成产物保留率 100%；
- 已取消任务直接恢复次数为 0，必须通过新任务重新开始；
- 每次业务工具调用和路由结果均可追溯；
- 通过外部 Agent 粘贴的原始材料可在 `drafts/` 找到，未调用工具时不得产生“已执行”证据；
- 同一 `task_id` 的确认回复可由不同外部 Agent 宿主继续执行；
- 每次评测结果均记录 Git commit、Prompt 版本、Skill 版本、模型和评测集版本；
- 至少完成一轮 Bad Case 修复与回归。

上述指标只描述当前 POC 测试集内的系统表现，不代表真实生产环境和业务效果。

## 16. 核心风险

| 风险 | 说明 | POC 控制方式 |
|---|---|---|
| 信息状态误判 | 将观点、提议或未确认数据当成事实 | 强制输出来源和成熟度，稳定写入需人工确认 |
| Context 污染 | 错误内容进入稳定 Context 后影响后续任务 | 分层存储、版本记录、确认门和回滚能力 |
| 过期信息干扰 | 历史内容继续冒充当前事实 | 时间和状态标签、替代关系、健康检查 |
| Agent 路由错误 | 选择错误任务模式或 Skill | 状态前置校验、结构化路由日志和评测集 |
| 过度自主 | Agent 替人决定业务方向和范围 | 明确人机边界，在关键节点强制确认 |
| PRD 幻觉 | 编造数据、规则或上下游关系 | 来源约束、待确认标签、独立审核 |
| 重规划失控 | 修改一个决策导致整份文档无差别重写 | 先做影响分析，再生成新计划，人工确认后执行 |
| 项目范围过大 | 同时建设企业级知识库、协作平台和多 Agent 系统 | 固定单用户、单活跃任务、通用项目工作区、6 个能力模块和隔离回归夹具 |

## 19. 当前基线结论

本项目不是“多个 Skill 的集合”，也不是“从一句想法生成 PRD”的内容工具。

其核心是：

> 通过 Context 工程管理 AI 的业务判断依据，由 Runtime 根据用户目标、信息成熟度和任务状态动态选择下一步，并由轻量 Harness 约束工具、状态、权限、人工确认和评测，使不同业务项目的 Context 维护与需求交付形成可持续改进的工作闭环。

本版本作为后续用户流程、状态机、架构、Skill、文件结构、Runtime 和评测设计的统一产品基线。
