# PRD 写作心法

> **来源**：从 PRD skills.md 迁移的实战经验，补充 prompt.md 的指导原则。

PRD 不是需求的堆砌，而是产品判断的体现。好的 PRD 源于清晰的产品思维。

---

## 核心心法

### 1. 先做减法再做加法 ⭐

**原则**：功能数量 ≠ 产品价值。

**实践**：
- 对每个功能追问："如果不做，用户会怎样？"
  - 如果答案是"也能用，就是不太方便" → 大概率不该放在 v1.0
- 写 PRD 前先列"明确不做"，比列"要做"更重要
- 三个相似需求 → 找到 1 个本质问题 → 解决这 1 个

**反模式**：
- ❌ 用户提了 10 个需求，全部写进 PRD
- ❌ "先做了再说，反正也不复杂"
- ❌ 只写"在范围"，不写"明确不做"

**示例**：
```
❌ 错误：
  在范围：
  - 支持手动添加节点
  - 支持从模板添加节点
  - 支持从其他项目复制节点
  - 支持批量导入节点
  - 支持 AI 生成节点

✅ 正确：
  在范围：
  - 支持手动添加节点（解决核心问题：用户需要自定义节点）
  
  明确不做（v1.0）：
  - 从模板添加：当前无标准模板库，v2.0 考虑
  - 从其他项目复制：跨项目依赖复杂，暂不做
  - 批量导入：使用频率低（<5% 用户），优先级靠后
  - AI 生成：技术方案未验证，独立规划
```

---

### 2. 穿透用户的话找本质 ⭐

**原则**：用户说"我想要 X 功能"时，真正要问的是"你遇到了什么问题？"

**方法**：
- 用户需求 = 用户描述的解决方案（不是真正的需求）
- 真正需求 = 用户想要获得的进步（Job to be Done）
- 连续追问 5 次"为什么"，找到本质问题

**实践**：
```
用户："我想要批量删除节点"
  ↓ 为什么？
"因为测试时创建了很多无用节点"
  ↓ 为什么会创建很多无用节点？
"因为不确定节点结构，反复尝试"
  ↓ 为什么不确定节点结构？
"因为没有预览，保存后才知道对不对"
  ↓ 本质问题
真正需求：需要节点创建时的即时预览
```

**反模式**：
- ❌ 用户说什么就写什么
- ❌ 把用户的解决方案当成需求
- ❌ 不追问背景和动机

**示例**：
```
❌ 错误：
  用户反馈："希望支持导出 Excel"
  PRD：支持导出 Excel 格式的攻击树

✅ 正确：
  用户反馈："希望支持导出 Excel"
  追问：为什么需要 Excel？（用户回答：需要给管理层汇报）
  追问：管理层需要什么信息？（用户回答：攻击树统计数据）
  本质需求：需要攻击树的统计分析功能
  PRD：支持生成攻击树统计报告（包含节点数量、层级分布、风险等级分布等）
```

---

### 3. 与现有系统保持一致 ⭐

**原则**：新功能的交互模式、术语、状态指示应与现有系统一致，降低用户学习成本。

**方法**：
- 写 PRD 前先看相关模块的功能层文档（`context/01_产品Context/`）
- 检查同类功能的交互模式（如其他"新建"功能怎么做的）
- 复用现有术语、组件、业务规则

**实践**：
```
写"攻击树手动添加节点"PRD 前：
1. 读 context/01_产品Context/B_TARA/攻击树.md
2. 看其他"添加"功能的 PRD（如"添加威胁场景"）
3. 对照术语表，确认"节点"/"元素"/"组件"的用法
4. 复用通用对话框交互模式
```

**反模式**：
- ❌ 不看现有系统，直接写自己理解的交互
- ❌ 创造新术语（如把"攻击树节点"叫"攻击点"）
- ❌ 重新发明轮子（明明有标准对话框，非要设计新样式）

**一致性检查清单**：见 `consistency-rubric.md` 的 6 个维度。

## 辅助心法

### 4. 不是找到正确的答案，而是找到正确的问题

- 解决错误的问题，做得再好也没有意义
- PRD 开头先写"要解决的问题"，而不是"解决方案"

### 5. 用户说什么不重要，用户做什么才重要

- 行为数据比用户访谈更诚实
- 有数据支撑的需求优先级更高

### 6. 完美是好的敌人

- 80% 完成度的功能今天发布 > 100% 的功能永远不发布
- CORE 阶段不追求细节完美，先对齐主体结构

---

## 应用：写 PRD 的顺序

按心法指导，推荐的写作顺序：

```
1. 先写"要解决的问题"（心法 2：穿透用户的话）
   ↓
2. 再写"明确不做"（心法 1：先做减法）
   ↓
3. 对照现有系统，确定交互模式（心法 3：保持一致）
   ↓
4. 写"在范围"和"核心流程"（聚焦本质问题）
   ↓
5. CORE 确认后，再补充细节（心法 6：不追求完美）
```

---

## 反模式总结

| 反模式 | 正确做法 |
|--------|---------|
| 用户提 10 个需求全写进 PRD | 找到 1 个本质问题，解决这 1 个 |
| 把用户的解决方案当需求 | 追问 5 次"为什么"，找本质 |
| 不看现有系统，直接写新交互 | 先读 context，复用现有模式 |
| 只写"在范围"，不写"不做" | "明确不做"和"在范围"同等重要 |
| 追求细节完美，CORE 写 100 页 | CORE 只写主体，DETAILS 再补充 |
| 无数据支撑，凭感觉写优先级 | 有数据 > 无数据，行为 > 访谈 |
