# PRD 分阶段规则

> **配置文件**：业务规则的单一事实来源在 `stage-rules.json`，本文档为人类可读版本。
> **版本**：0.4.0（对齐 PRD skills.md）

经 CP-R01 批准返回 `PRD_DRAFTING_CORE` 或 `PRD_DRAFTING_DETAILS` 时，允许基于快照中的 `approved_prd_base_version` 创建修订版本。只修改影响报告列出的章节，其他章节保持不变；CP-R01 不能替代修订后的独立审核和 CP-P03。

## CORE 必需章节

见 `stage-rules.json` 的 `stages.CORE.requiredSections`（10 个章节）：

0. **元信息**：标题、版本、状态、负责人（可选）
1. **背景与问题**：当前面临什么问题？
2. **产品目标与非目标**：我们要达成什么？明确不要达成什么？
3. **目标用户与场景**：这是给谁用的？典型使用场景？
4. **本期范围与明确不做**：在范围内的功能 + 明确不做的功能
5. **核心用户流程**：分步流程（用户动作 → 系统响应）
6. **功能概述**：高层次功能列表，每个功能一句话描述
7. **非功能需求**：性能（业务视角）、安全（访问控制）、可用性
8. **已确认决策**：经 CP-P01 确认的关键决策
9. **待确认信息**：需要后续确认的内容

CORE 不要求完整功能规则、异常分支、权限和验收矩阵。

## CORE 禁止内容

见 `stage-rules.json` 的 `stages.CORE.forbiddenSections`：

- 功能详细规则
- 角色与权限
- 边界与异常
- 验收用例
- 研发自测用例
- 典型验收用例
- 数据结构

**禁止模式**：`功能详细规则|角色与权限|边界与异常|验收用例|研发自测|典型验收|数据结构`

## CORE 关键检查点

见 `stage-rules.json` 的 `stages.CORE.checkpoints`：

- 功能范围是否明确
- 核心流程是否完整
- 功能逻辑是否清晰

## DETAILS 必需章节

见 `stage-rules.json` 的 `stages.DETAILS.requiredSections`（保留 CORE 全部 + 10 个新章节）：

10. **功能详细规则与状态**：详细的功能规则、状态定义、计算逻辑
11. **角色和权限**：按角色定义的权限矩阵
12. **边界与异常处理**：数据缺失、网络错误、并发冲突等异常情况
13. **研发自测用例**：5 个左右正向流程用例，简单易执行
14. **典型验收用例**：5-15 个关键场景（正向、异常、边界）
15. **验收标准**：功能完整性、数据准确性、性能要求的清单
16. **上下游依赖**：依赖哪些模块的数据，数据如何同步
17. **数据结构与兼容性**：新增/修改的字段、兼容性考虑
18. **数据与效果验证**：效果指标、数据埋点
19. **发布前待办**：上线前必须完成的事项

## 章节编写指南

### 元信息（CORE）
- **必需**：标题、版本、状态
- **可选**：负责人、创建日期、最后更新
- **格式**：简洁的键值对或表格

### 功能概述（CORE）
- **粒度**：每个功能一句话（不超过 30 字）
- **禁止**：不展开规则、异常、权限、交互细节
- **示例**：
  - ✅ “节点管理：支持创建、编辑、删除项目节点”
  - ❌ “节点管理：点击新建按钮后弹出表单，输入名称和描述，点击保存后调用 API...”

### 非功能需求（CORE）
- **视角**：业务要求，而非技术指标
- **性能**：从用户体验角度（”2秒内响应”，而非”QPS 1000”）
- **安全**：访问控制规则（”仅管理员可导出”，而非”SHA-256 加密”）
- **可用性**：业务连续性（”支持离线使用”，而非”Redis 集群”）

### 研发自测用例（DETAILS）
- **数量**：5 个左右
- **特点**：正向流程为主，简单易执行
- **目的**：帮助开发者快速验证核心功能
- **格式**：前置条件、操作步骤、预期结果

### 典型验收用例（DETAILS）
- **数量**：5-15 个关键场景
- **覆盖**：正向流程、异常流程、边界情况
- **详细程度**：比研发自测用例更全面
- **格式**：前置条件、操作步骤、预期结果

### 验收标准（DETAILS）
- **格式**：清单形式（Checklist）
- **分类**：功能完整性、数据准确性、性能要求
- **可验证**：每一项都可以明确判断是否达成

### 数据结构与兼容性（DETAILS）
- **新增字段**：字段名、类型、说明
- **修改字段**：原规则 → 新规则
- **兼容性**：旧数据如何处理

## 事实纪律

见 `stage-rules.json` 的 `factDiscipline`：

- 稳定 Context 可作为事实，但仍需检查版本和适用范围。
- 人工确认决策可作为需求规则。
- workspace 中未确认内容必须显式标注待确认。
- 不得用”行业常见做法”补齐缺失业务规则。
